# 选型记录：为什么最后是 doocs/md

> **这是历史决策记录，不是当前文档。**
>
> 写这份计划时判断 doocs/md「没有可编程接口、只能参考思路」，后来实际拆开源码发现**这个判断是错的**——`packages/core` 是一套不依赖 Vue 的纯 TS 渲染内核，可以直接 import。项目最终就建立在它之上。
>
> 保留这份记录是因为里面的「微信端硬约束」清单至今有效，而且这段试错过程本身有参考价值。本项目的实际用法请看 [README](../README.md)。

## 最初的候选对比

| 项目 | 形态 | 有没有现成 MCP | 能否当库复用 | 主题 |
|---|---|---|---|---|
| stylewx (`wjunhere/stylewx`) | MCP + REST + Web 编辑器 | 有（`npx -y @stylewx/mcp-server`） | `@stylewx/core` 纯函数内核 | 26 套 |
| md2weixin (`yanxi123-com/md2weixin`) | API + CLI + Web monorepo | 无 | `md2weixin-core`（导出 `getHtml`） | 多套 + 字体组合 |
| **doocs/md** | Vue 网页应用 | 无 | **当时误判为不可复用，实际 `packages/core` 可以直接用** | 3 套 |
| WeMD | Next.js 应用 | 无 | 无 | 20 套（已被 stylewx 移植） |
| wxmp / marknice / bm.md | 前端应用或 CLI | 无 | 部分 | — |

## 最终选择 doocs/md 的理由

1. **渲染质量最好**，代码块、公式、图表这些细节是长期打磨过的，重写追不上。
2. **`packages/core` 确实可以脱离 Vue 单独用**——本项目 vendor 了它的 `packages/core/src` 和 `packages/shared/src`，跑在纯 Node 里。
3. **它是很多人正在维护的项目**，跟随上游比维护自己的 fork 划算。

代价是：`@md/mcp-server` 没有发布到 npm，必须用源码；且它的 monorepo 依赖很重。本项目的做法是把 `core` 单独 vendor 出来，而不是装整个 workspace。

## 微信端硬约束（至今有效）

这些是微信编辑器的实际过滤行为，做任何排版工具的兜底都要考虑：

- 正文禁 JS，交互只能靠内联 SVG + SMIL
- `position` / `filter` 会被硬剥；`transform` / `animation` / `box-shadow` / `float` 属灰色属性，可能失效
- 页内锚点 `href="#..."` 必然失效（errcode 45166），依赖 `id` 的写法会被剥离
- 外链图（非 mmbiz 域名）会被校验器提示，发草稿时需搬运到素材库
- 微信只支持二级列表，表格过宽需改成可横向滚动

除了上表之外，还有两个不那么显眼的坑：doocs/md 的主题 CSS 里的 shadcn 变量（如 `--foreground`）定义在 Web 端的 Tailwind 样式中，Node 侧渲染时全部缺失；而且微信编辑器不认现代写法的 `hsl()` 和 `color-mix()`。

这两件事本项目都已经处理好了，使用者不必关心。它们只在搭这个东西的时候才需要排查，所以没有写进 README。
