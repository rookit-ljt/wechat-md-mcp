# 可视化编辑器方案（待确认）

目标：本地起一个页面，左侧改 Markdown，右侧实时看公众号里的样子，右侧面板调格式，调完一键复制进微信后台。

## 一、技术形态

扩展现有 HTTP 服务（`src/server.ts`，默认 127.0.0.1:8788），新增 `web/` 目录放静态页面，由同一个 Node 进程托管。

**不引入 Vite / React / 构建步骤。** 理由是这个项目的立身之本是「clone → npm install → 能跑」，为一个页面套前端工具链会把它变成需要 build 的项目，且多出几百个依赖。用原生 JS + iframe 完全够。

代价：没有组件化，代码是命令式的。页面规模控制在 3 个文件（`index.html` / `app.js` / `style.css`）。

## 二、界面结构

三栏，见草图：

- **左：编辑区** — 打开本地 `.md`（文件选择器或拖入），带一排工具栏（H2 / 粗体 / 引用 / 代码 / 图片），点击插入对应 Markdown 语法
- **中：预览区** — 390px 手机框，模拟公众号正文宽度
- **右：格式面板** — 主题、主色、字号、行高、段间距、代码块主题、Mac 代码栏、行号、首行缩进、两端对齐、脚注引用、字数统计，底部自定义 CSS 编辑器
- **顶栏** — 文件名、保存状态、「复制富文本」「保存 HTML」「打开预览」按钮

## 三、实时预览怎么做到「实时」

- 输入防抖 250ms → `POST /render`
- **预览用 `inline: false`**（保留 `<style>` 标签），不用 juice 内联。两个原因：更快；juice 会丢掉伪元素和媒体查询，视觉上反而不完整
- 提供「内联模式」开关，切到 `inline: true`，用于确认真正粘贴进微信后的效果。这个差异是真实存在的，值得单独留个开关
- 渲染耗时 300–700ms，hljs 的 CSS 首次 fetch 后缓存，防抖后体感可接受
- 预览塞进 `iframe srcdoc`，隔离主题 CSS，避免它污染编辑器自己的 UI

## 四、服务端要改的

现有：`GET /health`、`GET /themes`、`POST /render`。新增：

| 路由 | 用途 |
| --- | --- |
| `GET /` | 编辑器页面 |
| `GET /web/*` | 静态资源 |
| `POST /open` | 打开本地 `.md` 并回传内容（浏览器拿不到任意路径） |
| `POST /save` | 写回 `.md`（带 `.bak` 备份） |
| `POST /clipboard` | 服务端调 osascript 写 `public.html` flavor |
| `GET /config` + `POST /config` | 读写格式配置（落盘 `.editor-state.json`） |

图片走 data URI 内联（见下），**不新增文件服务路由**，避免把本地任意路径暴露成 HTTP 接口。

## 五、两个必须解决的点

**1. 本地图片在预览里是裂图**

公众号只吃 https 图片，但你写文章时 `![](./images/01.png)` 是本地路径，预览会全裂。

方案：预览请求带 `baseDir`（`.md` 所在目录），服务端把本地存在的图片转成 data URI 内联进预览 HTML。**只用于预览**——微信不吃 data URI，复制时另给提示。

安全约束：只解析 `baseDir` 之下的路径，只认图片扩展名，防目录穿越。

**2. 剪贴板**

主路沿用已验证的服务端 osascript 路径（`POST /clipboard`）。浏览器端 `navigator.clipboard.write` 写 `text/html` 作为非 macOS 的降级，但不作为主要路径——它在不同浏览器上的 flavor 行为不一致，不值得为它牺牲确定性。

## 六、和 MCP 的闭环

这是让它不只是一个网页的关键：

- 新增 MCP 工具 `open_editor`：`{ path }` → 拉起服务 + 打开浏览器到 `http://127.0.0.1:8788/?path=...`
- 编辑器把调好的格式配置落盘到 `.editor-state.json`
- **之后我渲染任何文章都默认读这份配置** — 你在页面里调一次品牌配色，后续所有文章自动沿用，不用每次传参
- 内容改动写回 `.md`，我读到的永远是你最新编辑的版本

## 七、分期

| 阶段 | 内容 |
| --- | --- |
| P1 | 静态路由 + 页面骨架 + iframe 实时预览 + 防抖 |
| P2 | 格式面板 + 配置持久化 |
| P3 | 本地图片 data URI + 剪贴板 + 保存 HTML |
| P4 | MCP `open_editor` 工具 + 文档更新 |

P1 出来就能用了，后面可以按需停。

## 八、明确不做

**不做真正的富文本直改（WYSIWYG）。** 就是「选中文字点加粗」那种。原因：改完要反推回 Markdown，双向同步是 bug 温床；而且最终交付物是 HTML 不是 Markdown，做同步收益很低。

折中方案是工具栏插入语法 + 实时预览，改完立刻看到效果，够用。
